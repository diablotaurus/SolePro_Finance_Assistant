Приоритет 3 — Статистика: загрузка по диапазону дат

Ранее GetTransactionStatisticsUseCase загружал всю таблицу транзакций в память. Теперь для статистики за период грузится только нужное окно дат [предыдущий период … конец] через существующий find_by_date_range (постранично). Агрегация и фильтрация остаются в Python через тот же TransactionFilterSpecification — DRY и точное поведение сохранены.

Окно загрузки

PERFORMANCE

Добавлены helper'ы _previous_period (общий с расчётом сравнения периодов — DRY), _statistics_load_window и _load_transactions_in_range. Ветки «показать всё» и «поиск» не изменились.

Приоритет 4 — Деньги контрагента как Decimal

Поле CounterpartyResponseDTO.total_income было float — недопустимо для финансового ПО. Переведено на Decimal сквозным образом: от границы репозитория (get_transaction_aggregates) через mapper до DTO. На PostgreSQL это сохраняет точность SUM(Numeric), которую float() ранее терял.

Точность вместо float

APPLICATION
# DTO total_income: Decimal = Field(Decimal("0"), ...) # mapper total_income=Decimal(str(payload.get("total_income", 0))) # репозиторий (агрегаты) "total_income": Decimal(str(row.total_income or 0))

Все потребители проверены: форматирование :,.2f и float(...) корректно работают с Decimal; сравнения Decimal == float истинны.

Стабильность и гигиена

Предупреждение pydantic BaseSettings

INFRASTRUCTURE

Устаревший pydantic.BaseSettings (pydantic v2) прощупывался библиотекой dependency-injector и шумел в stderr. Добавлен официальный пакет-компаньон pydantic-settings — предупреждение устранено в источнике. Наш код BaseSettings не использует.

pyproject.toml — добавлен pydantic-settings>=2.0.0
